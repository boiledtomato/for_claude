I have created a Wed feed with Web log and Qradar LEEF format. And it successfully received the log.

Then I created a similar web feed with Admin Audit log but it doesn’t have LEEF format. Therefore I have selected all available formats but still not working.

Do I have to use another way to get ZIA’s audit log? How can ZIA send audit log to Qradar without using wed feed?

Hi @Venkata Prasad Reddy Thappeta​

To integrate ZIA Admin Audit logs with IBM QRadar without using a web feed, consider the following options:

1. Nanolog Streaming Service (NSS): Configure NSS to forward Admin Audit logs directly to QRadar. Supported formats include CSV or Tab-separated, but not LEEF:

2. Go to Administration > Nanolog Streaming Service.

Create an NSS feed for Admin Audit logs, set the QRadar IP/FQDN, port, and format.

Cloud NSS (Managed Service): Use Zscaler’s Cloud NSS for seamless, real-time log delivery to QRadar with reduced infrastructure management. Configure similar to standard NSS feeds.

3. API-Based Retrieval: Use ZIA APIs to programmatically pull Admin Audit logs (/auditlogEntryReport endpoint) in JSON format and convert them to LEEF using custom scripts if needed.

Please note that ZIA does not natively support the LEEF format for Admin Audit logs.

Thanks.

Data Privacy - Sensitive Data storage and processing

Scenario:

When customer set DLP rule which look for 'Credit card number' when file uploaded to 'onedrive (personal)' and when it detect for user activity result in rule trigger

Question:

1. Does ZScaler store that matched 'credit card number' in plain text at ZScaler's own logs, database? If no, how does it work at Zscaler end?

2. Does ZScaler push matched 'credit card number' along with log where customer SIEM (Azure Sentinel) integrated to receive logs (DLP Logs) from Zscaler?

https://www.zscaler.com/company/privacy-policy

so DON'T point me to this.

MikeRuiz

(Employee)

2 years ago

Hello Vaibhav_j,

We do not store the matching data in our own logs or database.  If you want the matching data that triggered the violation, you have several options depending on your subscription.  You could have an email alert go out from zscaler which would optionally include the trigger data and the violating payload (we would have this data temporarily in our outbound SMTP).  If you have a third party ICAP receiver we can send the data to that ICAP/ICAPS receiver.  We also offer a ZScaler ICAP receiver, called ZScaler Incident Receiver, which can receive the trigger data/violating payload and store it in your storage.  Lastly the ZScaler Workflow Automation tool gives you the ZScaler Incident Receiver for either AWS or Azure paired with a full Advanced Incident Workflow tool.  The ZWA tool stores all the trigger data and violating payload in your company Azure Blob or AWS S3 storage where your own IAM controls apply in addition to it's RBAC.

WE do not push trigger data to SIEM.  The transaction metadata entry in the SIEM will have a matching DLP hash so you can correlate the logs with the payload.  ZWA makes this a bit easier as it's all Zscaler.

Hi,

This is a bit of a complex task, but I recommend either migrating all your users to Azure first or setting up a different login domain in Azure IdP. For example, if your current domain is "

ABC.com

," you could use "

BCD.com

" as the login domain in Azure to separate the authentication processes.

Additionally, if users are already logged into ZCC using ADFS authentication and you configure Azure IdP with "

ABC.com

" as your company domain while setting the ADFS IdP domain to "any," all new authentication requests for "

ABC.com

" will be directed to Azure AD. It's crucial to ensure that any user attempting to log in with "

ABC.com

" is present in Azure AD after configuring the new IdP. Existing users currently logged into ZCC with ADFS will not be affected, but if they log out and try to log back in, they must exist in Azure IdP.

Hope this helps you.

Note: You cannot keep domain as "ANY" in all IdP and it can be configured in only one IdP. Also Please consult with your Zscaler SE or TAM before making any configurations.

For me, I'd actually start with the end goal of what you are trying to accomplish. If you are looking to block access from personal devices and only allow corporate devices or you need to understand how much traffic is going to corporate devices vs personal ones for example, there are a ton of different options you could do. I'm going to assume this is all ZIA traffic and for O365 resources, since that is what you used as an example.

If you have a mix of corporate and personal devices that have the client connector installed, checking device hostnames and models will help sort things out. You can also make use of various device posture checks like the hybrid  domain joined check combined with ZIA posture profiles to help sort out what is a corporate vs personal device. On the ZPA side of things, having users go through a user portal and force CBI is also an option, but I've found issues with accessing O365 resources in Isolation when your idp is also Azure AD/Entra (it results in a continuous loop). If your idp isnt Azure AD/Entra though, that might work. You would want to ensure that O365 only accepts traffic from Zscaler's data centers though.  That would cover both ZIA traffic and ZPA/CBI traffic.

Some of that seems overkill to me though. You would be potentially eating up a lot of bandwidth in the continuous syncing of things like Sharepoint or OneDrive in CBI, and some features might break that people rely on. Instead, I'd recommend using some of the internal capabilities for Azure AD/Entra and with conditional access policies where you restrict the ability for users to download or upload O365 files based on certain criteria. This has the added benefit of being able to force users to out of desktop native apps and into the web browser versions of things like Outlook, Teams, OneDrive, ect without massively driving up your Isolation data usage on something that  will definitely skyrocket that. I thought the conditional access part was the easier route, but thats going  vary depending on things like your idp and what the end goals are.

I went and had another thought on it.

So through the ZIA side with Identity Proxy for Cloud Apps, it says it right on the page that if a cloud app is your idp, you can't use it for identity proxy (

https://help.zscaler.com/zia/configuring-zscaler-identity-proxy-cloud-apps

). I missed it when i was trying this. So if Azure AD/Entra is your idp, it wont work for O365 related items. O365 looks to Azure AD/Entra first as the idp, because why wouldn't it. Then you tell Azure AD/Entra to look to Zscaler as the idp. If Zscaler is then set to look to Azure Ad/Entra as the idp, that causes the login loop that never resolves. If O365 could look to something else first instead of Azure AD/Entra, that would solve the problem but it also would never happen. If the cloud app is something like Salesforce or your idp isn't Azure AD/Entra, then it should work without issue.

On the ZPA side, I don't think you would run into the same issues because you aren't doing that identity proxy part. You sign into the User Portal through whichever methods, then the isolation session launches before any authentication takes place. As long as the isolation profile has "View Office Files in Isolation" enabled, and "Local Browser Rendering" and "Application Deep Linking" disabled, it should launch fine. But then you are still running into the issue of telling O365 to only accept traffic from Zscaler sources through probably a conditional access policy in Azure AD/Entra. I'd definitely recommend multiple break glass admin accounts where that doesn't apply in case the worst happens, and you would have to deal with the unintended consequences. You will also deal with the CBI data usage being a thing. The ZIA Identity Proxy stuff was an all or nothing situation, and going the route of User Portal/CBI does give you some granularity to slowly roll it out to users. But in the end, you need to do work in both ZPA and in O365 (or your specific cloud resource de jour) which is why I would recommend restricting O365 downloads directly from Azure Ad/Entra in this situation. It makes for an overall more simplified process. If your cloud resource isnt O365 or isn't a massive data hog, then going the ZIA Identity Proxy (if available) or User Portal/CBI route could make sense. With the User Portal/CBI route though, you will always have to do something with the cloud resource to restrict it from accepting traffic other than from Zscaler or some other trusted network.

Microsoft Entra Hybrid Join and StrictEnforcement Option

Dear Community,

I have a question regarding the use of Application Profiles.

I have two application profiles:

Profile A is designed for M365 tenant restrictions and does not bypass "login.microsoftonline.com."

Profile B contains settings that allow bypassing "login.microsoftonline.com" and is used for Microsoft Entra Hybrid Join.

The priority of the Profiles is such that A is ranked higher than B, and the assigned users are the same for both.

When enabling the Strict Enforcement option and installing ZCC, we can specify Profile B in the Policy Token.

As a result, "login.microsoftonline.com" would be bypassed before the user signs in,

But not after signing in, which leads me to believe that the tenant restriction would function as intended.

However, I would like to confirm if this configuration is supported.

I'm concerned about potential operational issues or other concerns due to the switching of profiles before and after user sign-in.

Thank you for your assistance.

Client Connector

Hi @yui iwase​

Yes, what you have quoted above would work.

My follow up question is, do you also require SIPA on the M365 traffic? (usually required by enterprises via MS conditional access)

In that case you can do an interesting setup.

Create just one single app profile with Machine Tunnel option enabled (you can also opt to authenticate the machine tunnel). With this approach you'll ensure M365 traffic is intercepted by ZPA and inspected by ZIA before breaking out again via ZPA App Connector Egress IP.

When machine tunnel is active (that is user has not logged into ZCC) you can access

login.microsoftonline.com

via ZPA SIPA.   The tenant restriction settings will

not apply

and the traffic will break out using ZPA App Connector ensuring SIPA.

When the user tunnel is active (that is user has logged in into ZCC) the tenant restriction settings

will apply

and the traffic will break out using ZPA App Connector ensuring SIPA.

One of the things I have seen in the wild has been Windows workstations with IPv6 Enabled causing this.

Due to the nature of IPv6 DNS it sometimes has a tendency to give external IP resolvers to clients using Azure resources even if the AD is local.

Not saying this will 100% fix anything, however based on experience, it would be a prudent test to disable IPv6 to validate.

You should go to ZIA -> Identity Providers -> Service Provider (SP) Option and update to latest

"Request Signing SAML Certificate"

"Replace SP Certificate"

and Save.

Make sure ZCC login is tested, after these changes, so Logout from a ZCC and do a login on ZCC.

@Durga Prasad​

Its been couple of months since you asked this question, but I still want to make sure someone else referring to this thread gets the answer.

For PRA certificate renewal, you can follow 2 approaches.

You already have the certificate and entire certificate bundle.

You currently do not have the renewed certificate.

Already have the certificate:

The certificate you get from your 3rd party CA, either does not have private key or the it if has a private key (.pfx format) then the private key is encrypted. ZPA admin portal needs the certificate with unencrypted private key. You will need to use tools like openssl to get the correct certificate.

The following command creates a combined certificate and unencrypted private key PKCS#12 file (.pfx):

openssl pkcs12 -export -in <certificate>.pem -inkey <unencrypted private key>.key -out <combined cert and key>.pfx

For example:

openssl pkcs12 -export -in cert.pem -inkey unencrypted.key -out combined.pfx

The following command converts the PKCS#12 file (.pfx) containing the combined certificate and unencrypted private key file to PEM format (.pem):

openssl pkcs12 -in <combined cert and key>.pfx -out <combined cert and key>.pem -nodes

For example:

openssl pkcs12 -in combined.pfx -out combined.pem -nodes

combined.pem certificate can then be uploaded to the ZPA admin portal.

2.--You currently do not have the renewed certificate

You can generate the CSR (certificate signing request) from the ZPA admi portal. When you generate a CSR via the ZPA admin portal, it creates a key pair. Private key stays on the ZPA admin portal and your CSR has the public Key. You submit the CSR to your CA and get the certificate. That certificate can be directly uploaded on the ZPA admin portal without the need to follow that process of combining the certificate, because now the private key is already with the ZPA portal.

Go to Configuration & Control > Certificate Management > Certificates > Create CSR

Hello @Virupaksha Rajapur​ ,

Thanks for the details — good troubleshooting so far.

It looks like the issue is likely caused by Zscaler

blocking or intercepting a sub-URL / SSO endpoint

used by

bluebeamstudio.com

during the authentication redirect. The HAR shows a

307 Temporary Redirect

, which is consistent with SSO/IdP redirects — if Zscaler’s SSL inspection or a security policy is interfering with that redirect (or the SAML/redirect endpoint), the application can show the error:

“Unable to determine user authentication method. Please contact your administrator.”

support.okta.com+1

Recommended immediate test (safe, quick):

Create a temporary

SSL inspection bypass

(or add to the SSL inspection bypass group) for the Bluebeam domain and any related SSO endpoints (for example any sso, auth, or login subdomains under

bluebeamstudio.com

) and test from a user’s home network. The Palo Alto KB describing an identical error caused by Zscaler blocking

sso.paloaltonetworks.com

. recommends the same approach.

Link:

https://knowledgebase.paloaltonetworks.com/KCSArticleDetail?id=kA14u000000HDvfCAG&lang=en_US

If SSL bypass is not possible quickly, try an

authentication bypass

(only for a short test window) for the same domains to confirm whether authentication traffic is being intercepted/blocked by Zscaler.

Capture the ZCC logs and browser HAR again while testing the bypass; verify the 307 redirect completes successfully and that the SAML/IdP endpoint is reachable from the client without the redirect being intercepted. (You already have ZCC/HAR — repeat after bypass to compare.)

support.okta.com

Why SSL bypass first?

SSL inspection can break SAML/redirect-based SSO flows if it alters headers, certificates, or redirects. For many vendors (including Palo Alto’s support case), placing the portal/SSO domain into an SSL inspection bypass group resolved the error. Authentication bypass is an alternative but less desirable as a permanent fix.

knowledgebase.paloaltonetworks.com+1

If bypass fixes the issue:

Make the SSL bypass permanent for the exact Bluebeam domain(s) and any IdP endpoints required by the application (keep the rule scoped to only those domains).

Document the change and inform security stakeholders; if your org requires inspection for that traffic, work with Bluebeam/IdP to identify a compatibility path (e.g., certificate pinning, allowlisting IdP endpoints, or using a Zscaler supported exception workflow).

If bypass does not fix the issue:

Share full HAR and ZCC logs for a failed attempt (with timestamps) so we can check whether the redirect or SAML payload is malformed or being blocked by another network device. Also ask the application support (Bluebeam) to confirm their IdP endpoints and any special headers/cookies required.

Hello @Luke Sheaves​ ,

The

Primary Email

attribute is mandatory in

ZIdentity

, so ensure that the SAML response includes it. You can verify this using a SAML tracer to confirm if it’s being received.

However, it’s

not mandatory in ZIA

, as ZIA uses only the

NameID

attribute for authentication.

Additionally, ask the

Google IDP administrator

to validate whether this attribute is being sent and marked as

“Yes.”

Although the Zscaler Root Certificate is installed via ZCC installation, the certificate still needs to be trusted as it is untrusted by default. This is required for SSL Inspection to work properly.

Go to

Keychain Access

On the left panel under "System Keychains", click on

System

then scroll down on the right until you find

Zscaler Root CA.

Right-click on the Zscaler Root CA and select

Get Info

In the new window, click on the drop-down arrow where it says

Trust,

then next to "When using this certificate:" click on the drop-down and make sure you select

Always Trust

. By default this might be as untrusted or system default

Close the window and test access to any HTTPS internet site

These are manual steps.  If you are setting en mass, you probably want to set via your MDM (ie: InTune)

Recommended beginner approach: Use a Custom URL Category

If you are new to ZIA, this is the cleanest way to learn.

Step 1:

Create a custom category for AI sites

In the ZIA admin portal, find the area for URL Categories / Custom URL Categories.

Create something like:

Name:

AI_Sites

URLs / Domains:

chat.openai.com

claude.ai

gemini.google.com

copilot.microsoft.com

You can add more later.

Step 2:

Go to URL Filtering Policy

Now go to the area where you create URL Filtering rules.

This is the policy type usually used for:

website categories

domain access decisions

allow / block by user, group, category

Step 3:

Create Rule 1 = Allow for Group X

Create a rule like this:

What this means

If:

user is in Group X

and site belongs to AI_Sites

then:

allow

Step 4:

Create Rule 2 = Block for everyone else

Create another rule:

What this means

If:

any user goes to AI_Sites

and they did not already match Rule 1

then:

block

Step 5:

Put the rules in the correct order

This is the most important part.

The order must be:

Allow AI for Group X

Block AI for Others

If you reverse them:

Block AI for Others

Allow AI for Group X

then the block may hit first and your allowed users will also get blocked.

Step 6:

Save and Activate

In ZIA, after making policy changes, make sure you:

Save

Activate

If you forget to activate, the policy may not actually apply.

Very simple policy evaluation diagram

Here is the easy mental model.

User browses to an AI site

ZIA identifies the user

ZIA checks the user's group membership

ZIA checks the URL/category

Rule 1: Is user in Group X AND category = AI?

|---- Yes ---> ALLOW

|---- No ----> Go to next rule

Rule 2: Is category = AI?

|---- Yes ---> BLOCK

|---- No ----> Continue to other rules / default access

## Short answer

**Adaptive Access Engine (AAE) is generally not sold as a separate standalone paid feature.**

It’s typically an **included platform capability** for customers using the right Zscaler architecture and license setup, but it may require:

- migration to **Zscaler Authentication Service / ZIdentity**

- use of the **Experience Center**

- **manual enablement/provisioning** by Zscaler

- appropriate **ZIA/ZPA licensing** for some enforcement actions

So in practice, I’d describe it as:

| Question | Answer |

|---|---|

| Is AAE “free”? | **Not exactly** as a universal free feature anyone can just turn on |

| Is it a separate paid SKU? | **Usually no**, not as a simple standalone add-on |

| Do you need licensing/prereqs? | **Yes** — platform, architecture, and sometimes tier-dependent capabilities matter |

| How to confirm for your tenant? | Ask your **Zscaler account team** or **Support** to verify enablement and entitlement |

## Training / webinars

Yes — there **are training resources and webinar-style sessions**, but they appear to be mostly part of broader Zscaler training rather than a dedicated standalone AAE course.

### What’s available

| Type | Availability |

|---|---|

| Official documentation | **Yes** — help portal articles on AAE concepts, profiles, and integrations |

| Zscaler Academy training | **Yes** — typically covered within admin/engineer training tracks |

| Standalone AAE course | **Doesn’t appear to be a major standalone certification/course** |

| Webinars / recorded sessions | **Yes** — feature introductions, office hours, and event sessions have covered AAE |

### Likely places to look

- **Zscaler Help Portal**

- **Zscaler Academy / University**

- **Zenith Live recordings**

- **Zscaler Office Hours / technical webinars**

- sessions covering:

- dynamic access controls

- continuous risk assessment

- posture/risk signal integrations

- SSF / identity and device signal workflows

## Best practical takeaway

If you're trying to use AAE internally, the best next question is:

1. **Is our tenant already eligible/enabled?**

2. **Do we have the required Auth Service / Experience Center migration done?**

3. **Which training path covers AAE for admins or engineers?**
