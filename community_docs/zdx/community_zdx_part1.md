ZDX Remote Packet Capture

We’ve all been there: you need a packet capture to solve a connectivity issue, but the user is offline or doesn't have the technical know-how to run the command.

This article walks you through the process of enabling a remote packet capture via the Zscaler One UI. They can be easily retrieved for analysis once the user is available.

Note :

To maintain data privacy and security, .pcap files are stored locally on the user's device rather than being uploaded directly to the Zscaler UI.

Within the Zscaler One UI, head to the

Analytics

(1) section and ensure the

Switch to Existing Reports

toggle (2) is enabled. From there, navigate to

Digital Experience Management

(3) >

Troubleshoot

(4) >

Diagnostics

(5).

Next, click ‘

Start New Diagnostics Session

'; in the top right corner.

Give the session a name, then select the target user and the active device where the test will be performed.

For the ‘

What would you like to run?

’ field, select

Packet Capture Probing

. Then, choose your preferred Duration; while the default is set to 60 minutes, you have the flexibility to run the capture for as little as 5 minutes or as long as 48 hours.

In the Configure Window, add any filters you want to apply. You may filter to capture for a specific host or port number. For example, add port 443 to filter the packet capture for https port traffic only.

Frames Size Limit

specifies the packet payload length. The default setting is 1514, which you can adjust based on your troubleshooting requirements.

Disk Space Limit

manages how much storage the PCAP files will occupy on the user's device (default is 1GB). ZDX manages this space using a two-file rotation system: it creates two sequential files, each taking up half of the total allocated space. For example, if you set a 500MB limit, ZDX generates two 250MB files. Once the 500MB total is exceeded, the oldest file is deleted to make room for the new one.

Network Interface

specifies which local adapters should have their traffic monitored.

After entering all the required details, click

Save

to initiate the session. While the capture is active, it will appear in the In Progress section of the dashboard. Once the session is finished, it will automatically move to the History section for your review.

Once the session is complete, expand the entry in the History section to review the generated File Path. This field indicates exactly where the logs are stored on the end-user’s device.

Depending on the operating system, you can typically find the packet captures in the following locations:

On the user’s Windows device, open File Explorer and navigate to

Local Disk (C:)

. Locate the ProgramData folder to access the logs. If the ProgramData folder is not visible, it is likely hidden; to reveal it, select the View tab from the top menu and check the box for Hidden items.

Once inside, open the Zscaler folder.

Locate the specific directory that matches the alphanumeric name provided in the session's File Path (e.g., log-1a2b3c). Open this folder to access your recorded packet capture files.

Packet capture files have the prefix CaptureAdapters (Windows can also have the prefix CaptureLWF), followed by a timestamp and the file extension .pcap.

To analyze the captured traffic, right-click the file and select Open with Wireshark.

From Reactive to Proactive with ZDX Device Health Dashboard

We’ve all been there: a user complains that their browser is "lagging" or their laptop feels "sluggish." After hours of manual troubleshooting, remote sessions, and log diving, you finally reach a frustrating conclusion—the endpoint is over-utilized, compromised, or simply outdated.

What if you could spot these issues before the user even opens a ticket?

We have built a solution that transforms how IT teams manage hardware:

the Device Health Dashboard

. This proactive tool identifies devices that are currently degrading or nearing their end-of-life, allowing you to maintain a healthy fleet and keep your employees productive without the traditional troubleshooting headache.

What is the Device Health Dashboard?

It uses existing user and device data to create a comprehensive device health scoreboard that monitors the performance of Windows and macOS devices. Rather than waiting for a complaint, IT admins can now:

Identify the root causes of poor performance across the organization.

Use granular usage data to decide which hardware actually needs a refresh, ensuring maximum cost-effectiveness.

Spot high CPU usage or memory leaks before they lead to a system crash.

The best part? Along with ZDX Remediation, you can resolve these performance bottlenecks remotely and silently, without ever interrupting the user’s workflow.

Let’s look at how this works in a real-world scenario.

At the top of the Device Health dashboard, devices are automatically categorized by their health status. We’ll start by focusing on the "Poor" category—these are the machines most likely to generate helpdesk tickets.

By selecting a device from the "Poor" list, we can jump into a detailed troubleshooting view.

On the User Overview page, we get an immediate snapshot of the device’s health score alongside its specific hardware specifications.

In this example, we see the ZDX Score is consistently trending downward. This is a clear indicator of a poor digital experience. When the ZDX score drops, application performance usually follows.

Navigating to the Device Performance tab provides the evidence we need.

In this case, the data tells a clear story: CPU utilization is "touching the ceiling." By looking at the process breakdown, we can see that

chrome.exe

is consuming nearly all available system resources.

There you have it. By using this dashboard you were able to identify the devices that needed attention.

How to deal with this further?

Identifying the problem is only half the battle. Traditionally, fixing a high-consumption process would require calling the user and requesting a remote session.

With

ZDX Remediation

, you can take action directly from the portal. You can deploy a custom PowerShell script to terminate the runaway process or clear the cache across one—or one thousand—affected machines simultaneously.

From the user’s overview page, select Run Remediation.

We have a custom script created and signed for termination of any Windows processes named ‘Kill Windows Processes’.

Execute the script and add the required parameter detail.

It will take a while for the script to be executed on the device. Once the progress bar completes, verify the script output. In this case, the process ‘chrome.exe’ terminates.

No phone calls, no remote sessions, and no downtime for the employee. You’ve identified a performance loophole and closed it before the user even realized there was a problem.

ZDX Remediations: What’s in the Toolkit?

In today’s hybrid work environment, IT and Helpdesk teams are often overwhelmed by repetitive device-level issues. From clearing full disk drives to restarting hung services, these "micro-tasks" eat up valuable time. Zscaler Digital Experience (ZDX) Remediations changes the game by allowing administrators to execute automated PowerShell scripts directly on endpoint devices, resolving issues at scale without ever needing a remote session.

In this post, we’ll explore the types of scripts available in ZDX and highlight the ones most commonly used to keep up with digital workplaces.

The Three Core Use-Cases of ZDX Remediation

Most remediation workflows fall into one of these three strategic pillars:

1.

Information Retrieval

: Before you can fix a problem, you have to find it. Information retrieval scripts are non-intrusive; they don't change anything on the user's device but instead pull granular telemetry that standard monitoring might miss.

These scripts use the

set-zoutput

cmdlet to pipe specific data from the PowerShell environment directly into the ZDX Admin Portal.

2.

Active troubleshooting

: This is the heart of remediation—taking a definitive action to resolve a known issue. Instead of the Helpdesk walking a user through 10 steps over the phone, the admin pushes a button.

These scripts execute commands that modify system states, clear stuck queues, or reset configurations. They use

set-zresult

to report back whether the fix was successful.

3.

Pre-written scripts for Developer tools

: This use-case ensures that the endpoint and the scripts are always "in sync" from a security perspective.

Common Examples includes:

Configure Windows environment for OpenSSL based applications (Ruby, Python, Git) to trust Windows certificate store

Import Zscaler root cert for Java system-wide trust store

Most Commonly Used ZDX Remediation Scripts

Based on deployment trends and common IT pain points, here are the go-to scripts in the ZDX library

Disk Cleanup

: Automatically purging temporary files and emptying the Recycle Bin to reclaim storage and improve system responsiveness.

Memory Triage:

Running a "Get Top 20 Processes" script to identify memory-hungry applications causing system lag.

Network Optimization:

Checking IPv6 status or enabling/disabling it to resolve specific connectivity conflicts.

Remote Connectivity Checks

: Performing an nslookup directly from the user's endpoint to verify DNS resolution from their specific network location.

Hardware Health Checks:

Proactively checking battery health, memory integrity, or CPU utlization to identify aging hardware before it fails.

Why It Matters

By leveraging these scripts, IT teams can:

Reduce Mean Time to Resolution (MTTR): Fix issues in seconds, not hours.

Eliminate Remote Sessions: Solve problems in the background without interrupting the user.

Scale Efficiency: One script can fix 1,000 devices as easily as it fixes one.

Whether you are using the vetted Predefined library or building your own Custom PowerShell toolkit, ZDX Remediations ensures that the "Digital Experience" stays high and the "Support Burden" stays low.

Decoding SaaS Application Performance with ZDX Real User Monitoring

Modern workplaces are no longer confined within four walls. Employees launch SaaS apps from coffee shops, hop on private web apps over home Wi-Fi, and expect every page to load instantly — regardless of where the bottleneck actually lives. For IT and Operations teams, this creates a major visibility gap. If a user in a home office experiences a slowdown, how do you measure what they actually

feel

versus what your servers are reporting?

That's exactly the gap Zscaler Digital Experience Real User Monitoring (RUM) is built to close.

What Is ZDX Real User Monitoring?

ZDX RUM is a passive, always-on monitoring capability that captures performance telemetry directly from real user sessions inside the browser. Instead of relying solely on synthetic probes that simulate transactions on a schedule, RUM observes 100% of actual user interactions with SaaS and private web applications — and reports back what users genuinely experienced.

It works through a lightweight browser extension, tightly integrated with the Zscaler Client Connector. The result is a near real-time stream of how every page, every click, and every API call is performing — across every user, location, and device in your environment.

In ZDX, RUM helps troubleshoot application performance by breaking down the "black box" of the browser session. Here is how those specific RUM factors are used to pinpoint application issues:

1. The Page Load Waterfall (Isolating the Delay)

When a user says an app is slow, RUM provides a "waterfall" breakdown of the entire request-to-render cycle. This allows you to see exactly where time is being spent.

2. Monitoring individual pages & API Impact

Modern web apps are rarely just one file; they call 50+ external APIs, fonts, and scripts (like Google Analytics or payment gateways).

Resource Timing: ZDX RUM tracks the performance of every individual resource called by the page.

Troubleshooting: You can identify if a specific third-party script (like a misconfigured chat widget) is blocking the rest of the page from loading, allowing you to tell the app owner exactly which component to disable or optimize.

3. Core Web Vitals (The "Experience" Signal)

Instead of just "speed," RUM uses Core Web Vitals to tell you

how

the app is failing the user. Core Web Vitals are a set of metrics that measure real-world user experience for loading performance, interactivity, and visual stability.

4. Real-Time Error Tracking

Unlike synthetic monitoring, which only checks the pages you tell it to, RUM sees every page a user visits.

If a specific user process (like "Checkout") is failing, RUM will surface the errors encountered by real users. You can see exactly which URL or API endpoint triggered the error.

5. Identifying Geographic or Browser-Specific Outages

Because RUM captures data from every session, you can filter performance by:

Browser Version: "Is the app only slow on Chrome 124?"

Operating System: "Is this a macOS-only rendering bug?"

Geography: "Are users in Singapore the only ones seeing high TTFB?" This helps you determine if the application's CDN/Front-door is misconfigured for a specific region or if a new browser update has broken the app's code.

Why It Matters

The shift to cloud and hybrid work has made the user's browser the new edge of the enterprise. If you can't see what's happening there, you can't fix it. ZDX Real User Monitoring transforms every user session into a continuous, high-fidelity signal.

ZDX RUM doesn't just monitor the web; it decodes it.

Understanding Network Intelligence

Picture this: It is 9:00 AM on a Tuesday when a primary ISP at the headquarter experiences a routing failure. Suddenly, your help desk is flooded with tickets of inaccessible SaaS applications. The application team confirms cloud stability and the network team can’t see past the corporate firewall. The clock is ticking, productivity is dropping, and no one knows where to look.

This chaotic global outage response is a common challenge when the internet serves as your corporate backbone. In this environment, the traditional toolset of pings, traceroutes, and phone calls to ISPs simply cannot keep up.

Zscaler Digital Experience (ZDX)

Network Intelligence

was engineered specifically to address these gaps. It provides end-to-end multi-path network visibility from Last Mile Internet Service Providers (ISPs) to Zero Trust Exchange to applications.

How Does it Work?

ZDX utilizes machine learning to analyze cloud probe data, such as latency, hop count, and packet loss, to define a standard for network health. By tracking deviations from this baseline, the system identifies anomalies and presents them through a visual interface. These visualizations use severity-based color coding to highlight issues, with yellow indicating moderate degradation and red signaling critical network problems.

Let’s walk through of how Network Intelligence works.

On the Network Dashboard, the top graph highlights the

Network Anomalies

over the past 14 days. From here, select the latest anomaly.

The

Regions by ZDX Score

will list the geolocations in the order of decreasing number of anomalies. Select the region on the top of the list.

For the selected location, select the time range on the ISP/ASN viewgraph to narrow down the output.

This highlights the hops which are showing anomalies; deviating from their known baselines. The pop up shows the latency baselines and how much deviation has happened over the selected time.

Click on

IP View

. It shares the IP details of both the endpoints.

The

Application Performance

table enlists the reachable applications with their ZDX score and baselines.

Scale Your Troubleshooting with ZDX Remediation

To solve the challenge of manual, one-on-one troubleshooting, ZDX Remediation enables the remote execution of scripts to automatically resolve multiple device issues at scale.

Beyond simple fixes, this feature allows you to diagnose critical endpoint health statistics and perform Zscaler-specific actions, such as enabling developer environments for certificate-related issues. This guide will walk you through the setup and a real-world scenario to get you started.

Navigating the Environment

Navigate to the Scripts Library:

Policies > Digital Experience Monitoring > Configuration > Scripts

You have two primary options for populating your library:

Pre-written Scripts - ZDX provides a library of vetted scripts for common tasks, ready for immediate deployment.

Custom Scripts -  For unique environment needs, you can upload your own PowerShell scripts. Note: For security compliance, all custom scripts must be digitally signed.

Let's assume you have received a support ticket stating ‘My web browser is taking way too long to load applications.’

Phase 1: Root Cause Analysis (RCA)

Open the user’s overview on the Zscaler Digital Experience (ZDX) UI and select the appropriate time range.

If applications are in the "Red Category," select one to investigate.

Leveraging the Root Cause Analysis, we find out High CPU Utilisation caused the disruption.

Moving to the device performance tab, note the CPU, memory and disk utilisation. In this case it has reached its capacity.

Chrome.exe

is identified as the top resource consumer.

What happens when the system resources are not available?

Virtual Memory relies on disk space for paging and swapping. When the disk is full, the system cannot page efficiently, causing a general stall in all processes—even basic logins and program launches.

Phase 2: Executing Remediation

Instead of remote-controlling the user's machine and manually deleting files, use the Remediation feature:

1.  On the User Overview page, click '

Run Remediation

' (top right corner).

2.  Configure the Job -

Give the job a descriptive name

Select the script

‘Clean disk and recycle bin’

Click Start

3.  You will be taken to the Job Status page. Allow a few minutes for the script to execute and the progress to update.

Phase 3: Verification

Once the status changes to **Success**, you can verify the results without leaving the portal:

You can also verify the local disk space by logging into the user’s device. The C: drive now has some free space.

By using ZDX Remediation, you transformed a potentially lengthy manual support session into a few clicks. The user’s device is now stabilisedi, disk space is recovered, and the ZDX score has returned to a healthy range—allowing the engineer to focus on more complex tasks while the user resumes their work without further interruption.

Optimizing Digital Experience with ZDX Real User Monitoring (RUM)

Understanding how users actually experience an application is the key to effective troubleshooting. Real User Monitoring (RUM) is a passive monitoring technique that captures data on how actual users interact with a website or application.

Unlike synthetic monitoring, which simulates behavior, RUM provides a real-world perspective on performance by tracking metrics like page load times, errors, and API response times directly from the user's browser. This guide will help you navigate RUM to identify and isolate bottlenecks quickly.

RUM focuses on the ‘Three Pillars’ of the web experience

Page Fetch & Load Times:

The raw time it takes to retrieve and render a page.

Core Web Vitals:

A set of three specific Google metrics that measure user-centric performance.

Largest Contentful Paint (LCP)

measures loading performance (how fast the largest image/text block appears). Target: < 2.5s.

Interaction to Next Paint (INP)

measures interactivity. Target: < 200ms.

Cumulative Layout Shift (CLS)

measures visual stability. Target: < 0.1.

Error Rates:

Real-time tracking of web page errors and impacted user counts.

Let’s assume hospital staff have reported an extensive delay when using a critical patient management application (`medcare.cloudzdx.net`). When clicking "Admit Patient," The page takes an unacceptable amount of time to render, degrading the experience for both staff and patients.

Phase 1: Identifying the Bottleneck

In the Zscaler XC portal, navigate to the Healthcare Application dashboard.

Review the dashboard for total page views, average page load time, and current error rates.

On the Real-User Performance tab, scroll down to the

Most Viewed Pages

section. Notice

/admit-patient

is the most visited web page with high latency.

Phase 2: Deep-Dive Analysis (The Drill-Down)

To understand why this is happening for specific users, we must look at individual sessions:

Select the /admit-patients link to review the users impacted by the issue.

Click on the eye icon to the waterfall chart for the impacted user.

Select a specific datapoint within the User page load summary graph.

You will be shown key details regarding

Core Web Vitals

, in addition to a Waterfall chart that illustrates the load time for each page resource.

Notice

Largest Contentful Paint (LCP)

measures the time it takes for the largest visual element (image, video, or large text block) to appear in the user's view.

Phase 3: Verification

The final step is determining if the issue is the Network, Zscaler, or the Application itself.

On the user’s overview page, scroll down to the application Cloudpath.

The Cloudpath reveals

no network latency

despite the 22-second slowdown, the issue is confirmed to be

application-related

So, by using ZDX RUM, we successfully deduced that the 22-second delay was an internal application fault, not a network or Zscaler connectivity issue.

The helpdesk can now bypass the network and Zscaler teams entirely, escalating the ticket directly to the

Application Support Team

. This targeted escalation eliminates "finger-pointing" between departments and significantly reduces the Mean Time to Resolution (MTTR).

More details on Core Web Vitals are available here:

https://developers.google.com/search/docs/appearance/core-web-vitals

Blocked due to Server Probe Failure

I found an interesting reason for a “Blocked due to Server Probe Failure?:

Users is a road warrior, who uses a PAC file with dedicated proxy port

SSL Inspection is disabled

SAML authentication is used

User has no authentication cookie and the source IP from the unknown location has not yet been “whitelisted?.

If the user now tries to access an https site, the redirect to the IDP does not work and the access is blocked (error message of browser, not a Zscaler block message) with “Blocked due to Server Probe Failure? indicated in the log file.

Solution: User has to access a http site to get the IP “whitelisted? for 2h. If the user cannot Access http sites, it might be possible that the browser DNS Cache / browser history has already stored an automatic redirect from http to https. To remove this, the user has to clear the histroy of the browser.

This will make the redirect to the IDP working.

Zscaler認定資格（Zscaler Certification）の受験方法

Zscaler認定資格のご紹介🏆

こんにちは。カスタマーサクセスマネージャの吉村です。

Zscaler認定資格についてご紹介します。

（こちらの記事は 2025/4/24 時点の情報になります）

Zscaler認定資格は、Zscaler管理者やゼロトラストセキュリティに関心がある方が対象の資格となります。

Zscaler認定資格を取得していただくと認定証が発行されます。

資格取得を通じてご自身のスキルアップであったり、会社での目標設定にするなどご活用していただければと思います。

なお、Zscaler認定資格はZscaler Cyber Academy から申込を行います。

初めて Zscaler Cyber Academyをご利用される方は先に

こちらの投稿

を御覧ください。

本日2025/4/24時点では以下のとおりです。

試験名 : Zero Trust Cyber Associate (ZTCA)

初めて受験する方におすすめの試験

ゼロトラストの概念から勉強したい方は、ZTCA の取得から目指すことをお勧めします。

既にZscalerを触ったことがある方は、ZDTA の取得から目指すことをお勧めします。

ZDTA は日本語でE-learning、ハンズオントレーニング、試験を受けることが出来るので、そういう意味でもここから始めるというのも良いかもしれません。

こちらの ZDTA 取得後に、上位試験である ZDTE の取得を目指すか、その他の専門性のある資格の取得を目指すか、という流れになっています。

なお、英語での試験問題はブラウザの翻訳機能を利用できません。

英語が苦手な方は大変だと思いますが、日本語での試験も今後増えていく予定ですので、ご期待ください。

学習方法

各試験にはLearning Pathが用意されています。

E−learningの長さはそれぞれ異なりますが、おおよそ10時間程度と想定するとよいでしょう。

また、クラウドサービスということもあるので、実際にZscalerクラウドにログインしてポータルを触ってみたり、E−learningコンテンツに登場する Practice Activity でデモ実演をこなすと、学習時の理解が深まると思います。

なお、EDU-xxx の番号がついている資格については、Learning Pathの受講が必須になっているため、資格受験の前に必ず完了しておかないといけません。

受験方法

1.　Zscaler Academyの各試験の詳細ページから「Register」をクリックします。

2.　購入数を確認し、「Review and Pay」をクリックします。

なお、EDUクレジットを利用して受験をされる際には、別途発行されるコードをこちらで入力して「Apply」を行ってください。

3.　クレジットカードでのお支払いの場合には、こちらにクレジットカード情報を入力して購入します。

なお、EDUクレジットでのお支払いの場合には、クレジットカードは必要ございません。

日本のお客様でEDUクレジットでのお支払いをご希望の場合には、日本のZscalerチームまでご連絡をください。

4.　お支払い完了後には、試験の詳細ページから「Exam」をクリックして試験を開始できます。

以上となります。

もし情報が古くなっていたらアップデートしますので、コメントを頂けると幸いです。

Is there a similar program to zscaler analyzer output or can it still be downloaded somewhere? I know its already EOL.

Dirk_Monge

9 months ago

Zscaler Analyzer has reached its End-of-Life (EOL), and downloads or new support are no longer available as of February 28, 2024. Existing instances are supported only until February 28, 2025.

Alternatives to Zscaler Analyzer:

Zscaler Digital Experience (ZDX): ZDX is the recommended tool to replace Zscaler Analyzer functionality. It offers advanced digital experience monitoring, including network and application performance diagnostics.

Speed Test Tool: Zscaler's speed test tool (

http://speedtest.zscaler.com/perf

) can be used for connection diagnostics and troubleshooting network performance.

Third-Party Tools: Tools like WinMTR (on Windows) are also suggested for performing  traceroute tests in environments no longer supported by the Analyzer.
